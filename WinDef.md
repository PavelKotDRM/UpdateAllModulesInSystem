# Срабатывание Microsoft Defender

Microsoft Defender может ошибочно определять Windows-сборку UpdateAllModules как:

```text
Trojan:Win32/Bearfoos.A!ml
```

Суффикс `!ml` означает, что решение принято эвристической моделью машинного обучения, а не точной сигнатурой известного вредоносного файла. Это не доказывает безопасность программы автоматически, поэтому каждое срабатывание необходимо проверять.

## Почему приложение вызывает подозрение

UpdateAllModules выполняет несколько действий, сочетание которых может повышать оценку риска для нового неподписанного EXE:

- запрашивает повышение прав через системный UAC;
- запускает PowerShell и Windows COM API для проверки Windows Update;
- запускает системные менеджеры пакетов и другие дочерние процессы;
- может скрывать консольное окно при работе GUI;
- распространяется как новый неподписанный Rust-бинарник без накопленной репутации.

В проекте не используются упаковщики, обфускация, UPX или загрузка и выполнение стороннего бинарного payload.

## Результаты диагностики

Снимок от 30.07.2026:

- Authenticode-статус release-файла: `NotSigned`;
- Defender был включён, защита в реальном времени работала;
- версия сигнатур Defender: `1.455.419.0`;
- версия движка: `1.1.26060.3008`;
- обнаруженная угроза после обработки имела состояние `IsActive: False`.

SHA-256 проверенной локальной сборки:

```text
C6E0A09D3CE1FD033D4B243328FAAC10D457BA088A5B09A05769D7468B096FC6
```

Этот хэш относится только к одной конкретной сборке. После изменения исходного кода, версии компилятора или зависимостей хэш будет другим.

## Проверка файла

Проверить хэш:

```powershell
Get-FileHash .\update_all_modules.exe -Algorithm SHA256
```

Проверить Authenticode-подпись:

```powershell
Get-AuthenticodeSignature .\update_all_modules.exe | Format-List
```

Проверить состояние Microsoft Defender:

```powershell
Get-MpComputerStatus | Select-Object `
  AntivirusEnabled,
  RealTimeProtectionEnabled,
  AntivirusSignatureVersion,
  AntivirusSignatureLastUpdated,
  AMEngineVersion,
  AMProductVersion
```

Для проверки происхождения рекомендуется собирать программу самостоятельно из доверенной копии репозитория:

```powershell
cargo build --release --locked
Get-FileHash .\target\release\update_all_modules.exe -Algorithm SHA256
```

Различие хэшей локальной и опубликованной сборок само по себе не означает заражение: Rust-сборки могут зависеть от версии toolchain, ОС, метаданных сборки и состояния исходного кода.

## Отправка ложного срабатывания

Файл следует отправить Microsoft как ошибочно классифицированный:

1. Открыть [Microsoft Security Intelligence: Submit a file](https://www.microsoft.com/en-us/wdsi/filesubmission).
2. Выбрать тип отправителя **Software developer**.
3. Загрузить обнаруженный EXE.
4. Указать детект `Trojan:Win32/Bearfoos.A!ml`.
5. Выбрать вариант ошибочного обнаружения безопасного файла.
6. Добавить ссылку на исходный код, релиз и соответствующий commit/tag.
7. Указать SHA-256 загруженного файла.

После исправления классификации Microsoft может потребоваться обновить сигнатуры Defender и пересобрать либо повторно скачать release-файл.

## Подпись Windows-сборки

Основной способ снизить количество ложных срабатываний и подтвердить издателя — подписывать каждый release доверенным сертификатом Authenticode с отметкой времени.

Пример с сертификатом в PFX:

```powershell
signtool sign `
  /f certificate.pfx `
  /fd SHA256 `
  /td SHA256 `
  /tr http://timestamp.digicert.com `
  .\target\release\update_all_modules.exe
```

Проверка подписи:

```powershell
signtool verify /pa /v .\target\release\update_all_modules.exe
```

`SignTool` входит в Windows SDK. Для публичных релизов нужен сертификат от доверенного центра сертификации или сервис доверенной облачной подписи. Самоподписанный сертификат не создаёт доверия на компьютерах пользователей, пока его корневой сертификат не установлен вручную.

Закрытый ключ и пароль PFX нельзя хранить в репозитории. В CI следует использовать защищённые secrets, аппаратный ключ или облачный signing-сервис. Подписывать нужно готовый EXE до упаковки в ZIP.

Официальная документация: [SignTool — Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool).

## Дополнительные меры

- Добавить в PE-файл название продукта, версию, издателя и иконку.
- Публиковать SHA-256 рядом с каждым GitHub Release.
- Собирать релизы только через контролируемый CI из tag и `Cargo.lock`.
- Не применять UPX, обфускацию и нестандартные упаковщики.
- После каждой сборки проверять Authenticode-подпись и хэш артефакта.
- При повторном срабатывании отправлять Microsoft именно тот файл, который распространяется пользователям.

## Чего делать не следует

Не следует рекомендовать пользователям:

- отключать Microsoft Defender;
- отключать защиту в реальном времени;
- добавлять весь каталог загрузок или проекта в исключения;
- игнорировать различие хэшей и происхождение файла.

Для локальной диагностики допустимо временное исключение только конкретного проверенного файла, однако перед распространением правильнее добиться исправления классификации и подписывать релизы.
