
# Техническое задание: Кроссплатформенная утилита для комплексного обновления системы, сред разработки и пакетов Python с поддержкой CLI и GUI

## 1. Назначение и цели проекта

Разработка кроссплатформенного приложения на языке Rust для автоматизации проверки и установки обновлений. Программа должна агрегировать в едином интерфейсе управление обновлениями операционной системы, пакетного менеджера Python (`pip`), а также изолированных утилит разработчика (`rustup`, `msys2` и др.).

Приложение должно поддерживать два режима работы:

1. **Интерфейс командной строки (CLI)** — для автоматизации, использования в скриптах и работы на серверах.
2. **Графический интерфейс (GUI)** — для удобного интерактивного использования на персональных компьютерах.

## 2. Область применения и поддерживаемые инструменты

Программа должна автоматически сканировать систему на наличие следующих инструментов и управлять их обновлением:

* **Системные менеджеры (Windows):** `winget`, `choco` (Chocolatey).
* **Системные менеджеры (Linux/macOS):** `apt`, `dnf`, `pacman`, `brew` (Homebrew).
* **Среды разработки и утилиты:** * `rustup` (обновление тулчейнов Rust).
* `msys2` (Windows: обновление окружения через вызов его внутреннего `pacman`).


* **Python:** Глобальный или пользовательский `pip` (вызов через `python -m pip` для обеспечения стабильности путей).

## 3. Архитектура и режимы запуска (Dual-Mode Architecture)

Приложение компилируется в единый бинарный файл. Логика определения режима запуска строится на анализе аргументов командной строки:

1. **CLI-режим:** Активируется, если при запуске переданы любые аргументы командной строки (например, `-c`, `--check`, `-y`, `--only-tools`).
2. **GUI-режим:** Активируется по умолчанию, если программа запущена без аргументов (например, при двойном клике по иконке в проводнике Windows или macOS Finder, либо при запуске в терминале без флагов).
3. **Явный вызов GUI:** Добавить флаг `--gui`, принудительно открывающий графическое окно, даже если переданы другие параметры.

Для Windows-сборки необходимо предусмотреть корректное скрытие или отображение консольного окна (настройка `#![windows_subsystem = "windows"]` динамически или управление консолью через WinAPI при переключении режимов).

## 4. Интерфейс командной строки (CLI)

Реализуется с помощью библиотеки `clap`.

**Доступные флаги и параметры:**

* `-c, --check` — Только проверка (вывод таблицы доступных обновлений).
* `-y, --yes` — Автоматическое согласие на все обновления (тихий режим для скриптов).
* `--gui` — Принудительный запуск графического интерфейса.
* `-v, --verbose` — Вывод подробного лога и потоков выполнения внешних утилит.
* **Фильтрация:** `--skip-system`, `--skip-pip`, `--skip-tools` или инверсные флаги (`--only-tools`, `--only <NAME>`).

## 5. Графический интерфейс (GUI)

Реализуется на базе библиотек **`egui`** и **`eframe`** (официальный фреймворк для запуска `egui`).

**Требования к UI-элементам:**

* **Главный экран:** * Кнопка «Проверить обновления» (запускает сканирование во внешнем потоке, чтобы GUI не зависал).
* Кнопка «Обновить всё» (активна после проверки или доступна сразу).
* Чек-бокс «Автоматическое согласие (-y)».


* **Сводная таблица/список модулей:**
* Каждый менеджер/инструмент (`winget`, `pip`, `rustup`) отображается отдельным блоком/строкой.
* Индикация статуса: *«Не найден в системе»*, *«Актуален»*, *«Доступны обновления (X пакетов)»*.
* Возможность развернуть блок, чтобы увидеть список конкретных устаревших пакетов (например, для `pip` или `winget`).
* Индивидуальные чек-боксы напротив каждого инструмента для выборочного обновления.


* **Окно логов/прогресса:**
* Интегрированная в нижнюю часть окна или всплывающая текстовая панель (Console Log), куда перенаправляется `stdout` и `stderr` запущенных процессов обновлений в реальном времени.



## 6. Требования к функциональности (Бэкенд)

### 6.1. Абстракция модулей (Trait `Updater`)

Вся бизнес-логика изолирована от интерфейса через Rust-трейт:

```rust
pub trait Updater {
    fn name(&self) -> &'static str;
    fn is_installed(&self) -> bool;
    fn check_updates(&self) -> Result<Vec<PackageUpdate>, UpdaterError>;
    fn apply_updates(&self, force_yes: bool, log_sender: &std::sync::mpsc::Sender<String>) -> Result<(), UpdaterError>;
}

```

### 6.2. Управление многопоточностью

* Все тяжелые операции (`check_updates`, `apply_updates`) в GUI-режиме должны выполняться в отдельных потоках (`std::thread` или через пул задач).
* Данные о прогрессе и строки логов должны передаваться в поток GUI через каналы (`std::sync::mpsc` или `crossbeam-channel`) для отрисовки в реальном времени.

### 6.3. Управление привилегиями

* Приложение должно определять уровень прав (`root`/Администратор).
* **Разделение прав:** Программа не должна требовать запуск от Администратора/root в обязательном порядке для старта. Если права обычные — GUI/CLI выводит предупреждение, что системные пакеты (APT/Choco) будут пропущены или могут упасть, но `pip` (пользовательский) и `rustup` смогут обновиться успешно.

## 7. Обработка ошибок, логирование и кодировка

* **Кодировка в Windows:** При перехвате `stdout` от `winget` или `msys2` на Windows необходимо обрабатывать кодировки отличные от UTF-8 (например, OEM CP866 или Windows-1251). Рекомендуется использовать библиотеку `encoding_rs`.
* **Изоляция сбоев:** Падение одного процесса (например, сетевой сбой при обновлении пакета в `pip`) не должно приводить к крашу всей программы или GUI-окна. Ошибка фиксируется в логе, статус модуля меняется на «Ошибка», и выполнение переходит к следующему инструменту.

## 8. Требования к технологическому стеку

* **Язык:** Rust (Edition 2021).
* **Ключевые зависимости (Crates):**
* `clap` — парсинг CLI.
* `egui` и `eframe` — графический интерфейс и контекст окна.
* `anyhow` / `thiserror` — обработка ошибок.
* `serde` & `serde_json` — парсинг JSON вывода (от `pip list --outdated --format=json`).
* `is_elevated` — проверка прав Администратора.
* `encoding_rs` — работа с системными кодировками Windows.
* `comfy-table` — для красивого вывода таблиц в CLI-режиме.



## 9. Примерный сценарий использования (User Flow)

### Сценарий 1: Запуск через GUI (двойной клик)

1. Пользователь запускает приложение. Открывается окно `egui`.
2. Программа автоматически запускает экспресс-сканирование (`is_installed`).
3. Пользователь видит список: `Winget` (Доступно 3 обновления), `Rustup` (Требует обновления), `Pip` (Все пакеты актуальны).
4. Пользователь нажимает «Обновить выбранное». Появляется встроенное окно терминала с бегущим логом выполнения `winget upgrade...`, а затем `rustup update`.
5. По завершении выводится плашка: «Обновление успешно завершено».

### Сценарий 2: Запуск через CLI (Автоматизация)

1. В CI/CD или планировщике задач вызывается: `my-updater --check --skip-system`
2. Программа определяет наличие аргументов, окно GUI **не инициализируется**.
3. В консоль выводится отформатированная таблица доступных обновлений для `pip` и инструментов разработчика. Программа завершает работу.
